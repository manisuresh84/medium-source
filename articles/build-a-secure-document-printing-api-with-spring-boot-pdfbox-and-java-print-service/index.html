Build a Secure Document Printing API with Spring Boot, PDFBox, and Java Print Service

A practical server-side pipeline for securely converting and printing PDF, Word, text, RTF, and HTML documents

By Suresh Kumar Mani

2026-07-31

Printing from a web application sounds simple until the requirements become real. The application must accept several formats, reject unsafe uploads, preserve layout, locate a server-side printer, apply print settings, and report failures without exposing confidential data.

This tutorial builds that pipeline with Spring Boot 3, Java 21, Apache PDFBox, and the Java Print Service API. The guiding principle is straightforward: convert every supported document to PDF, then maintain one dependable printing path.

This is server-side printing. The job goes to a printer installed for the operating-system account running the Spring application. It does not open the browser print dialog or automatically reach a printer connected only to the user's laptop.

Architecture overview

The architecture deliberately separates five responsibilities: accepting the request, validating and routing the document, converting it into a common PDF representation, controlling printer selection and capabilities, and handing the final job to the operating-system printing stack.

The left side is the untrusted boundary. An authenticated client submits multipart/form-data to POST /print. PrintController enforces authorization and rejects invalid filenames, excessive size, disallowed extensions, and path-traversal patterns before a document parser sees the bytes.

DocumentType then routes the validated upload into a format-specific conversion lane:

  • existing PDF files are loaded and structurally validated;
  • DOC and DOCX files are rendered by a Word-compatible layout engine;
  • RTF is processed by an RTF-aware layout renderer;
  • HTML and XHTML are sanitized before XHTML-to-PDF rendering;
  • TXT receives an explicit font, line wrapping, margins, and pagination through PDFBox.

Every lane converges on the same contract: a readable, non-encrypted PDF with a valid %PDF- signature and an allowed page count. This is the most important architectural decision in the application. It prevents format-specific logic from leaking into printer discovery and job submission.

After normalization, PrinterSelector finds only the configured, allowlisted queue and checks whether it is accepting work. Capability negotiation compares requested options—paper size, copies, color, quality, orientation, duplex, and page range—with what that queue reports.

Finally, PDFBox exposes the validated document as PDFPageable, Java PrinterJob sends the rendered pages to the operating-system spooler, and Windows or CUPS hands the job to the installed driver and physical or virtual printer.

The application can truthfully report SUBMITTED_TO_SPOOLER after successful submission. It should not claim PRINTED unless the printer platform provides a trustworthy device-level completion signal.

What we are building

The application exposes POST /print and accepts a multipart file. The authenticated caller must have the USER role. The service validates the upload, converts non-PDF formats, finds the configured printer, builds supported printer attributes, and renders the PDF through PDFBox.

The processing stages are:

  1. Authenticate and authorize the request.
  2. Validate the uploaded filename, size, extension, and content.
  3. Convert DOC, DOCX, TXT, RTF, HTML, or XHTML to PDF.
  4. Discover an approved operating-system printer.
  5. Negotiate paper, color, copies, orientation, duplex, and page-range settings.
  6. Submit the job and return a durable job identifier.

The resulting architecture is intentionally layered:

Step 3: Secure the API

For a machine-to-machine service, stateless HTTP Basic authentication is a compact demonstration:

@Bean
SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/error").permitAll()
            .requestMatchers("/print/**").hasRole("USER")
            .anyRequest().authenticated())
        .httpBasic(basic -> basic.realmName("Print Service"))
        .csrf(csrf -> csrf.ignoringRequestMatchers("/print/**"))
        .sessionManagement(session -> session
            .sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .build();
}

CSRF policy must match the authentication model. A stateless Basic-auth endpoint can be exempt, while a browser session authenticated by cookies generally needs CSRF protection. Encode the selected policy in tests so configuration and expectations cannot drift apart.

Security work before production

  • Require authentication and the USER role.
  • Limit multipart requests to 10 MB.
  • Reject path separators and traversal sequences in filenames.
  • Integrate enterprise identity and per-printer authorization.
  • Scan uploads for malware.
  • Enforce page-count, memory, conversion-time, and concurrency limits.
  • Add secure-release printing for confidential documents.

Step 4: Validate uploads at the boundary

Extension allowlisting is the first layer, not the entire defense:

private static final Set<String> ALLOWED_TYPES =
    Set.of("pdf", "doc", "docx", "txt", "rtf", "html", "xhtml");

private void validateFile(MultipartFile file) {
    if (file == null || file.isEmpty()) {
        throw new SecurityException("File is null or empty");
    }

    String name = file.getOriginalFilename();
    if (name == null || name.isBlank()) {
        throw new SecurityException("File name is missing");
    }

    if (name.contains("..") || name.contains("/") || name.contains("\\")) {
        throw new SecurityException("Illegal filename");
    }

    if (file.getSize() > 10L * 1024 * 1024) {
        throw new SecurityException("File exceeds 10 MB");
    }
}

Production validation should inspect magic bytes, parse with bounded resources, remove active HTML content, and block remote resource loading. Never write an upload using the caller-supplied filename.

Step 5: Keep the controller thin

The controller validates the request and delegates the printing work:

@PostMapping(consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
@PreAuthorize("hasRole('USER')")
public ResponseEntity<String> printDocument(
        @RequestParam("file") MultipartFile file,
        Principal principal) throws Exception {

    validateFile(file);
    printService.printDocument(file.getOriginalFilename(), file.getBytes());
    return ResponseEntity.accepted().body("Print job accepted");
}

202 Accepted means the service accepted the work. It does not prove that paper emerged from the device. A production API should return a job ID and provide a status resource such as GET /print/jobs/{id}.

Step 6: Normalize every format to PDF

The printer should receive one predictable representation regardless of what the caller uploaded. PDF is a useful normalization format because it fixes page geometry, fonts, images, and pagination before the operating-system printer driver becomes involved.

Create one converter component with a small public method. Keep the format-specific methods private so callers cannot accidentally bypass common validation.

@Component
public class FileToPdfConverter {
    private static final int MAX_PAGES = 250;

    public byte[] convert(byte[] input, DocumentType type) throws IOException {
        if (input == null || input.length == 0) {
            throw new IllegalArgumentException("Document content is empty");
        }

        byte[] pdf = switch (type) {
            case PDF -> validateAndCopyPdf(input);
            case DOC, DOCX -> convertWord(input);
            case RTF -> convertRtf(input);
            case HTML, XHTML -> convertHtml(input);
            case TXT -> convertText(input);
        };

        validateGeneratedPdf(pdf);
        return pdf;
    }
}

Use an enum rather than passing arbitrary strings throughout the service:

public enum DocumentType {
    PDF, DOC, DOCX, TXT, RTF, HTML, XHTML;

    public static DocumentType fromFilename(String filename) {
        if (filename == null || filename.isBlank()) {
            throw new IllegalArgumentException("Filename is required");
        }

        int dot = filename.lastIndexOf('.');
        if (dot < 0 || dot == filename.length() - 1) {
            throw new IllegalArgumentException("Filename has no extension");
        }

        String extension = filename.substring(dot + 1).toUpperCase(Locale.ROOT);
        try {
            return DocumentType.valueOf(extension);
        } catch (IllegalArgumentException exception) {
            throw new IllegalArgumentException(
                "Unsupported document extension: " + extension, exception);
        }
    }
}

Extension detection controls routing, but it does not establish trust. Verify the content signature as well. For example, PDF begins with %PDF-, legacy DOC usually uses the OLE compound-document signature, DOCX is a ZIP package with required Word entries, and RTF begins with {\\rtf. Let the selected parser reject structurally invalid content.

Convert existing PDF files

Do not blindly return uploaded PDF bytes. Load the document to verify structure, reject encryption when the service does not support passwords, enforce a page limit, and save a clean copy.

private byte[] validateAndCopyPdf(byte[] input) throws IOException {
    try (PDDocument document = PDDocument.load(input)) {
        if (document.isEncrypted()) {
            throw new IllegalArgumentException("Encrypted PDFs are not supported");
        }
        if (document.getNumberOfPages() == 0) {
            throw new IllegalArgumentException("PDF contains no pages");
        }
        if (document.getNumberOfPages() > MAX_PAGES) {
            throw new IllegalArgumentException("PDF exceeds the page limit");
        }

        ByteArrayOutputStream output = new ByteArrayOutputStream();
        document.save(output);
        return output.toByteArray();
    }
}

Loading a PDF is structural validation, not malware scanning. Run untrusted documents through an approved scanner and keep PDFBox patched.

Convert DOC and DOCX files

DOC is the older binary Word format; DOCX is an Open Packaging Convention ZIP containing XML parts. Apache POI is excellent for reading and editing Office documents, but it is not a complete layout engine. Accurate printing requires a renderer that understands fonts, headers, tables, floating images, sections, and Word pagination.

The inspected project uses Aspose.Words. Load the license once during application startup, then create a new Document for every conversion:

@Component
public class WordConverter {
    private final com.aspose.words.License license;

    public WordConverter(ResourceLoader resources) throws Exception {
        this.license = new com.aspose.words.License();
        Resource resource = resources.getResource("classpath:license.xml");
        try (InputStream stream = resource.getInputStream()) {
            license.setLicense(stream);
        }
    }

    public byte[] convert(byte[] input) throws IOException {
        try (InputStream source = new ByteArrayInputStream(input);
             ByteArrayOutputStream target = new ByteArrayOutputStream()) {

            com.aspose.words.Document wordDocument =
                new com.aspose.words.Document(source);

            // Update fields such as page numbers and table of contents.
            wordDocument.updateFields();
            wordDocument.save(target, com.aspose.words.SaveFormat.PDF);
            return target.toByteArray();
        } catch (Exception exception) {
            throw new IOException("Word-to-PDF conversion failed", exception);
        }
    }
}

Delegate from the main converter:

private final WordConverter wordConverter;

private byte[] convertWord(byte[] input) throws IOException {
    return wordConverter.convert(input);
}

Fonts used by the source document must exist in the conversion environment or be explicitly mapped. Test tables, page breaks, headers, footers, embedded images, equations, and non-Latin text. If commercial licensing is unsuitable, a common alternative is an isolated LibreOffice headless worker. Do not start a new LibreOffice process for every HTTP request; use a bounded worker pool and timeouts.

Convert RTF files

RTF contains formatting instructions, fonts, colors, tables, and embedded objects. Converting it by reading it into Swing and writing it back does not reliably produce HTML; RTFEditorKit.write writes RTF syntax, not an HTML rendition.

Aspose.Words can auto-detect and render RTF directly, which preserves more layout and removes the unreliable RTF-to-HTML intermediate step:

private byte[] convertRtf(byte[] input) throws IOException {
    try (InputStream source = new ByteArrayInputStream(input);
         ByteArrayOutputStream target = new ByteArrayOutputStream()) {

        LoadOptions options = new LoadOptions();
        options.setLoadFormat(LoadFormat.RTF);

        com.aspose.words.Document rtfDocument =
            new com.aspose.words.Document(source, options);
        rtfDocument.save(target, SaveFormat.PDF);
        return target.toByteArray();
    } catch (Exception exception) {
        throw new IOException("RTF-to-PDF conversion failed", exception);
    }
}

If using LibreOffice instead, write the RTF to a private temporary directory, invoke the converter with a strict timeout, validate the resulting PDF, and securely remove both files afterward.

Convert HTML and XHTML files

HTML conversion has two independent concerns: security and layout. Jsoup can sanitize markup, while iText XML Worker can render a limited XHTML/CSS subset. Sanitizing and rendering are not the same operation.

First decode UTF-8 and remove active or remote content with an explicit allowlist:

private String sanitizeHtml(byte[] input) {
    String html = new String(input, StandardCharsets.UTF_8);
    if (html.isBlank()) {
        throw new IllegalArgumentException("HTML document is blank");
    }

    Safelist allowed = Safelist.relaxed()
        .addTags("table", "thead", "tbody", "tfoot", "tr", "th", "td")
        .addAttributes(":all", "class")
        .addAttributes("td", "colspan", "rowspan")
        .addAttributes("th", "colspan", "rowspan")
        .addProtocols("a", "href", "https");

    Document.OutputSettings outputSettings = new Document.OutputSettings()
        .syntax(Document.OutputSettings.Syntax.xml)
        .charset(StandardCharsets.UTF_8)
        .prettyPrint(false);

    return Jsoup.clean(html, "", allowed, outputSettings);
}

This example deliberately excludes scripts, iframes, forms, styles, local-file URLs, and remote images. If images are required, download them through a controlled fetcher that blocks private networks, applies byte and time limits, verifies image content, and supplies local bytes to the renderer. Allowing the renderer to fetch arbitrary URLs creates a server-side request forgery risk.

Next render sanitized XHTML:

private byte[] convertHtml(byte[] input) throws IOException {
    String xhtml = sanitizeHtml(input);

    try (ByteArrayOutputStream target = new ByteArrayOutputStream()) {
        com.itextpdf.text.Document pdf = new com.itextpdf.text.Document(
            com.itextpdf.text.PageSize.A4, 45, 45, 50, 50);
        PdfWriter writer = PdfWriter.getInstance(pdf, target);
        pdf.open();

        try (InputStream markup = new ByteArrayInputStream(
                xhtml.getBytes(StandardCharsets.UTF_8))) {
            XMLWorkerHelper.getInstance().parseXHtml(
                writer,
                pdf,
                markup,
                StandardCharsets.UTF_8,
                new XMLWorkerFontProvider(XMLWorkerFontProvider.DONTLOOKFORFONTS));
        }

        pdf.close();
        return target.toByteArray();
    } catch (Exception exception) {
        throw new IOException("HTML-to-PDF conversion failed", exception);
    }
}

XML Worker and iText 5 are older technologies with licensing constraints and limited modern CSS support. For complex HTML, consider a maintained renderer or a sandboxed browser-based PDF worker. Whichever engine you choose, pin versions, disable uncontrolled network access, and test the exact CSS subset you promise.

Convert plain-text files

Plain text has no page model. The converter must choose paper size, margins, font, font size, line spacing, wrapping, and pagination. The following PDFBox 2.x implementation embeds a Unicode TrueType font from src/main/resources/fonts/NotoSans-Regular.ttf.

private byte[] convertText(byte[] input) throws IOException {
    String text = new String(input, StandardCharsets.UTF_8)
        .replace("\r\n", "\n")
        .replace('\r', '\n');

    try (PDDocument document = new PDDocument();
         InputStream fontStream = getClass().getResourceAsStream(
             "/fonts/NotoSans-Regular.ttf")) {

        if (fontStream == null) {
            throw new IllegalStateException("Unicode font resource is missing");
        }

        PDType0Font font = PDType0Font.load(document, fontStream, true);
        PDRectangle pageSize = PDRectangle.A4;
        float margin = 50f;
        float fontSize = 11f;
        float leading = 15f;
        float usableWidth = pageSize.getWidth() - (2 * margin);

        List<String> visualLines = new ArrayList<>();
        for (String logicalLine : text.split("\n", -1)) {
            visualLines.addAll(wrapLine(logicalLine, font, fontSize, usableWidth));
        }

        PDPageContentStream stream = null;
        float y = 0;
        try {
            for (String line : visualLines) {
                if (stream == null || y < margin + leading) {
                    if (stream != null) {
                        stream.endText();
                        stream.close();
                    }

                    if (document.getNumberOfPages() >= MAX_PAGES) {
                        throw new IllegalArgumentException("Text exceeds page limit");
                    }

                    PDPage page = new PDPage(pageSize);
                    document.addPage(page);
                    stream = new PDPageContentStream(document, page);
                    stream.beginText();
                    stream.setFont(font, fontSize);
                    y = pageSize.getHeight() - margin;
                    stream.newLineAtOffset(margin, y);
                }

                stream.showText(line);
                stream.newLineAtOffset(0, -leading);
                y -= leading;
            }
        } finally {
            if (stream != null) {
                stream.endText();
                stream.close();
            }
        }

        ByteArrayOutputStream target = new ByteArrayOutputStream();
        document.save(target);
        return target.toByteArray();
    }
}

Wrap each logical line by measuring rendered glyph width rather than counting characters:

private List<String> wrapLine(
        String line,
        PDFont font,
        float fontSize,
        float maximumWidth) throws IOException {

    if (line.isEmpty()) return List.of(" ");

    List<String> result = new ArrayList<>();
    StringBuilder current = new StringBuilder();

    for (String word : line.split("\\s+")) {
        String candidate = current.isEmpty() ? word : current + " " + word;
        float width = font.getStringWidth(candidate) / 1000f * fontSize;

        if (width <= maximumWidth) {
            current.setLength(0);
            current.append(candidate);
        } else {
            if (!current.isEmpty()) result.add(current.toString());
            current.setLength(0);
            current.append(word);
        }
    }

    if (!current.isEmpty()) result.add(current.toString());
    return result;
}

For production, also split a single word that is wider than the page, replace unsupported control characters, detect malformed UTF-8 rather than silently replacing it, and use PDFBox's newer APIs if upgrading to PDFBox 3.

Validate every generated PDF

Every format-specific method ends at the same postcondition: a readable, non-empty, bounded PDF.

private void validateGeneratedPdf(byte[] pdf) throws IOException {
    if (pdf == null || pdf.length < 5 ||
            pdf[0] != '%' || pdf[1] != 'P' ||
            pdf[2] != 'D' || pdf[3] != 'F' || pdf[4] != '-') {
        throw new IOException("Converter did not produce a PDF document");
    }

    try (PDDocument document = PDDocument.load(pdf)) {
        int pages = document.getNumberOfPages();
        if (pages < 1 || pages > MAX_PAGES) {
            throw new IOException("Generated PDF page count is outside limits");
        }
    }
}

Wire conversion into the print service

The orchestration layer now has no format-specific printing branches:

@Service
public class PrintService {
    private final FileToPdfConverter converter;
    private final PrinterService printerService;

    public void printDocument(String filename, byte[] content) throws Exception {
        DocumentType type = DocumentType.fromFilename(filename);
        byte[] pdf = converter.convert(content, type);

        javax.print.PrintService printer = printerService.fetchPrintService();
        printerService.printPdf(pdf, printer);
    }
}

That is the value of normalization: PDF, Word, RTF, HTML, XHTML, and TXT all converge before printer discovery and job submission.

Why convert every document to PDF before printing?

It may seem wasteful to convert a Word, RTF, HTML, or text document when the target printer might accept some of those formats. The conversion step is actually the architectural boundary that makes the printing service predictable.

Printers do not share one document language

Java Print Service exposes DocFlavor values reported by each installed driver. One printer may advertise PDF, another may accept only PAGEABLE, and another may claim AUTOSENSE while producing different results depending on its Windows or CUPS driver. Native DOCX and RTF support is especially uncommon because those formats require a full document-layout engine, not just a printer driver.

If the application sends every original format directly, it needs a matrix of paths:

Input Possible native path Common problem
PDF Driver PDF support Not consistently advertised
DOC/DOCX Office automation Requires Word/Office and an interactive profile
RTF Driver or desktop application Formatting varies by renderer
HTML/XHTML Browser or HTML print service CSS, fonts, headers, and margins differ
TXT Text flavor No standard wrapping, margins, or pagination

Five inputs multiplied by several printer models quickly becomes a large compatibility and test matrix. Normalization changes the model to many inputs → one PDF contract → one printing path.

PDF establishes a page model

Word and HTML are reflowable. Their final page breaks depend on fonts, available page width, margins, renderer behavior, and sometimes the default printer. Plain text has no page geometry at all. PDF fixes the important output decisions before submission:

  • physical page size and orientation;
  • font selection, embedding, and glyph positions;
  • line wrapping and page breaks;
  • image size and placement;
  • headers, footers, tables, and vector graphics;
  • the exact number and order of pages.

The printer driver still rasterizes or translates those pages for the device, but it no longer decides how a DOCX paragraph or HTML table should flow.

One format creates one validation checkpoint

Every converter must return a PDF that can be reopened, has at least one page, stays under the page limit, and is not encrypted. That gives the service a measurable postcondition before it spends spooler resources. A failed HTML render and a corrupt Word document are reported as conversion failures rather than mysterious printer errors.

One format simplifies operations

PDF normalization also provides:

  • one PDFBox rendering implementation;
  • consistent page-range behavior;
  • a previewable intermediate representation;
  • repeatable conversion tests;
  • clearer audit stages: VALIDATED, CONVERTED, QUEUED, and SUBMITTED;
  • easier migration between Windows printing, CUPS, a cloud print API, or archival storage.

There are tradeoffs. Conversion consumes CPU and memory, requires fonts and licensed renderers, and may not reproduce every advanced Word or CSS feature perfectly. Keep the original document only as long as policy requires, isolate converters, and compare representative documents against known-good output. The goal is not “PDF is universally perfect”; it is “PDF gives this service one controlled, testable page contract.”

Step 7: Discover an approved printer

Java Print Service represents an operating-system print queue through javax.print.PrintService. Discovery returns queues visible to the identity running the JVM—not necessarily the printers visible to the developer's interactive desktop.

Wrap the static lookup API so the rest of the application can be unit-tested:

public interface PrinterRegistry {
    List<javax.print.PrintService> availablePrinters();
}

@Component
public class JavaPrinterRegistry implements PrinterRegistry {
    @Override
    public List<javax.print.PrintService> availablePrinters() {
        return List.of(PrintServiceLookup.lookupPrintServices(null, null));
    }
}

Select only a configured printer. Do not accept an unrestricted printer name from an HTTP request because that lets callers enumerate or target any queue available to the service account.

@Service
public class PrinterSelector {
    private final PrinterRegistry registry;
    private final PrinterProperties properties;

    public javax.print.PrintService selectConfiguredPrinter() {
        String requested = properties.getName().trim();

        return registry.availablePrinters().stream()
            .filter(printer -> printer.getName().equalsIgnoreCase(requested))
            .findFirst()
            .orElseThrow(() -> new PrinterUnavailableException(
                "Configured printer is not installed or visible: " + requested));
    }

    public List<String> visiblePrinterNamesForDiagnostics() {
        return registry.availablePrinters().stream()
            .map(javax.print.PrintService::getName)
            .sorted(String.CASE_INSENSITIVE_ORDER)
            .toList();
    }
}

Expose printer names only through an administrator-only diagnostic endpoint, and consider printer names sensitive infrastructure information.

Check queue state before submitting

A discovered queue may be stopped or rejecting new work. Inspect the standard attributes when the driver provides them:

public void requireAvailable(javax.print.PrintService printer) {
    PrinterIsAcceptingJobs accepting =
        printer.getAttribute(PrinterIsAcceptingJobs.class);
    PrinterState state = printer.getAttribute(PrinterState.class);
    QueuedJobCount queued = printer.getAttribute(QueuedJobCount.class);

    if (PrinterIsAcceptingJobs.NOT_ACCEPTING_JOBS.equals(accepting)) {
        throw new PrinterUnavailableException(
            "Printer is not accepting jobs: " + printer.getName());
    }

    if (PrinterState.STOPPED.equals(state)) {
        throw new PrinterUnavailableException(
            "Printer queue is stopped: " + printer.getName());
    }

    int queueDepth = queued == null ? -1 : queued.getValue();
    LOGGER.info("Printer selected: name={}, state={}, queueDepth={}",
        printer.getName(), state, queueDepth);
}

Many drivers return null for attributes they cannot report. Treat unknown state separately from a known failure; do not interpret null as proof that the physical device is ready.

Failing closed is safer than silently choosing the default printer. An unexpected fallback could place a confidential document in another department. If fallback is a business requirement, configure one explicit fallback queue, authorize it, and record the failover in the audit event.

Understand deployment identity

Printer discovery commonly fails after deployment because the service runs as a different account:

  • a Windows service may not see printers installed only for a desktop user;
  • a Linux service needs access to the CUPS server and queue;
  • a container usually has no host print subsystem unless it is deliberately connected;
  • network printers may require credentials, drivers, DNS, and firewall access.

Run a startup health indicator under the real service identity. It should confirm that the configured queue is visible without actually printing a page.

Step 8: Map configuration to Java print attributes

Java Print Service expresses job options as typed Attribute objects. The application must translate every supported configuration value explicitly.

@Component
@ConfigurationProperties(prefix = "printer")
public class PrinterProperties {
    private String name;
    private int copies = 1;
    private String mediaSize = "ISO_A4";
    private String chromaticity = "MONOCHROME";
    private String printQuality = "NORMAL";
    private String orientation = "PORTRAIT";
    private String duplex = "ONE_SIDED";
    private String pageRange = "";
    private String jobName = "Document_Print_Job";

    // Getters and setters omitted.
}

Create candidates from configuration:

private List<Attribute> requestedAttributes() {
    List<Attribute> requested = new ArrayList<>();
    requested.add(new Copies(properties.getCopies()));
    requested.add(new JobName(
        properties.getJobName(), Locale.getDefault()));
    requested.add(parseMedia(properties.getMediaSize()));
    requested.add(parseChromaticity(properties.getChromaticity()));
    requested.add(parseQuality(properties.getPrintQuality()));
    requested.add(parseOrientation(properties.getOrientation()));
    requested.add(parseSides(properties.getDuplex()));

    if (properties.getPageRange() != null &&
            !properties.getPageRange().isBlank()) {
        requested.add(new PageRanges(properties.getPageRange()));
    }
    return requested;
}

Map strings with strict switches so a typo fails during validation rather than silently changing output:

private MediaSizeName parseMedia(String value) {
    return switch (value.toUpperCase(Locale.ROOT)) {
        case "ISO_A4" -> MediaSizeName.ISO_A4;
        case "ISO_A5" -> MediaSizeName.ISO_A5;
        case "LETTER", "NA_LETTER" -> MediaSizeName.NA_LETTER;
        case "LEGAL", "NA_LEGAL" -> MediaSizeName.NA_LEGAL;
        default -> throw new IllegalArgumentException(
            "Unsupported configured media size: " + value);
    };
}

        case "COLOR" -> Chromaticity.COLOR;
        case "MONOCHROME" -> Chromaticity.MONOCHROME;

Negotiate capabilities with the selected queue

Configuration describes what the caller wants; the printer decides what it supports. Test every attribute against the selected queue and the PAGEABLE flavor used by PDFBox:

private PrintRequestAttributeSet supportedAttributes(
        javax.print.PrintService printer) {

    DocFlavor flavor = DocFlavor.SERVICE_FORMATTED.PAGEABLE;
    PrintRequestAttributeSet accepted =
        new HashPrintRequestAttributeSet();

    for (Attribute attribute : requestedAttributes()) {
        boolean supported = printer.isAttributeValueSupported(
            attribute, flavor, accepted);

        if (supported) {
            accepted.add(attribute);
            continue;
        }

        if (attribute instanceof MediaSizeName ||
            attribute instanceof Sides) {
            throw new IllegalArgumentException(
                "Printer does not support required option: " + attribute);
        }

        LOGGER.warn("Omitting unsupported print attribute: printer={}, value={}",
            printer.getName(), attribute);
    }
    return accepted;
}

The policy above treats paper size and duplex as mandatory and other options as optional. Adjust that rule for the business case. For legal documents, selecting the wrong media or one-sided output may be a hard failure.

To help administrators diagnose a queue, enumerate supported categories and values:

for (Class<?> category : printer.getSupportedAttributeCategories()) {
    Object values = printer.getSupportedAttributeValues(
        category, DocFlavor.SERVICE_FORMATTED.PAGEABLE, null);
    LOGGER.debug("Printer capability: category={}, values={}",
        category.getSimpleName(), values);
}

Some capabilities are vendor-specific. Paper trays often appear as MediaTray values returned by the driver rather than portable string constants. Discover and map them by a controlled configuration identifier; do not assume MANUAL_FEED exists on every device.

Step 9: Render normalized PDF pages with PDFBox

PDFBox implements Java's Pageable contract. PDFPageable supplies each PDF page to PrinterJob, which delegates final rasterization and transport to the installed driver.

@Service
public class PrinterService {
    private final PrinterSelector selector;
    private final PrinterAttributeFactory attributes;

    public void printPdf(byte[] pdfBytes) throws IOException, PrinterException {
        javax.print.PrintService printer =
            selector.selectConfiguredPrinter();
        selector.requireAvailable(printer);

        try (PDDocument document = PDDocument.load(pdfBytes)) {
            if (document.isEncrypted()) {
                throw new IllegalArgumentException(
                    "Encrypted PDF cannot be printed");
            }

            PrinterJob job = PrinterJob.getPrinterJob();
            job.setPrintService(printer);
            job.setJobName(attributes.jobName());
            job.setPageable(new PDFPageable(document));

            PrintRequestAttributeSet request =
                attributes.forPrinter(printer);

            LOGGER.info(
                "Submitting print job: printer={}, pages={}, attributes={}",
                printer.getName(), document.getNumberOfPages(), request);

            job.print(request);

            LOGGER.info(
                "Print job returned from spooler submission: printer={}",
                printer.getName());
        }
    }
}

The PDDocument must stay open until job.print() returns because PDFPageable reads and renders pages during that call. Closing it immediately after setPageable() causes failures during printing.

Pageable printing versus raw PDF submission

Two Java printing approaches are easy to confuse:

  1. PrinterJob plus PDFPageable renders the PDF through PDFBox and uses the service-formatted PAGEABLE flavor.
  2. DocPrintJob plus SimpleDoc sends bytes using a flavor such as DocFlavor.BYTE_ARRAY.PDF.

Raw submission is appropriate only when printer.isDocFlavorSupported(DocFlavor.BYTE_ARRAY.PDF) is true and the target device or queue reliably handles PDF. The PDFBox PAGEABLE path is more portable because the Java/AWT print pipeline supplies rendered pages.

Do not use AUTOSENSE as evidence that arbitrary DOCX, HTML, or RTF bytes will print correctly. It delegates interpretation to the driver, and behavior varies across environments.

Optional job events for a native DocPrintJob path

DocPrintJob supports a PrintJobListener:

DocPrintJob job = printer.createPrintJob();
job.addPrintJobListener(new PrintJobAdapter() {
    @Override
    public void printDataTransferCompleted(PrintJobEvent event) {
        LOGGER.info("Print data transferred to the spooler");
    }

    @Override
    public void printJobCompleted(PrintJobEvent event) {
        LOGGER.info("Print subsystem reported job completion");
    }

    @Override
    public void printJobFailed(PrintJobEvent event) {
        LOGGER.error("Print subsystem reported job failure");
    }

    @Override
    public void printJobCanceled(PrintJobEvent event) {
        LOGGER.warn("Print job was canceled");
    }

    @Override
    public void printJobRequiresAttention(PrintJobEvent event) {
        LOGGER.warn("Print job requires operator attention");
    }
});

These callbacks describe what the print subsystem reports. Driver behavior is inconsistent, and “completed” may still mean the queue finished processing rather than a human collected a physical page.

Define job states honestly

PrinterJob.print() returning without an exception usually means the driver or spooler accepted the rendered job. It does not prove:

  • the printer had paper and toner;
  • every page physically printed;
  • the output was not canceled later;
  • the document reached the intended tray;
  • a user collected a secure-release job.

Use states that reflect observable facts:

RECEIVED -> VALIDATING -> CONVERTING -> READY_TO_PRINT
         -> SUBMITTING -> SUBMITTED_TO_SPOOLER
         -> FAILED_VALIDATION | FAILED_CONVERSION | FAILED_SUBMISSION

Only introduce PRINTED when the printer platform supplies a trustworthy device-level completion signal. Store the normalized error category and correlation ID, but return a safe message to the API caller.

Prevent duplicate physical output

Retries are dangerous after spooler submission. If the application times out after the queue accepted the job, submitting again may print a duplicate. Use an idempotency key before conversion, persist state transitions transactionally, and make operators reconcile an ambiguous submission instead of automatically retrying it.

Transient conversion failures can often be retried safely because no physical side effect occurred. Submission failures need a more conservative policy based on whether the spooler assigned a job identifier or the call failed before transfer.

Step 10: Test without wasting paper

Use a virtual PDF printer or an isolated test queue. Mock the application printing service in controller tests, then verify:

  • unauthenticated requests return 401;
  • callers without USER return 403;
  • valid uploads return 202;
  • malicious filenames and unsupported types return 400;
  • oversized multipart requests return 413;
  • internal exceptions return a stable response without stack traces.

Converter tests can assert that output begins with %PDF-, load it with PDFBox, and verify page count. Wrap static printer discovery behind an adapter so unit tests never depend on printers installed on a developer workstation.

Production architecture

For high-volume printing, move conversion and spooler calls away from the HTTP thread:

  1. Validate and store the upload in protected temporary storage.
  2. Create a durable job record.
  3. Place the job on a bounded queue.
  4. Scan and convert it in an isolated worker.
  5. Submit it to an authorized printer.
  6. Update job state and audit information.
  7. Delete source and intermediate files according to retention policy.

This model supplies backpressure, retries, visibility, and clear failure states. Record the authenticated user, job ID, document size, printer, requested options, timestamps, and outcome—but never log document contents.

Conclusion

A dependable printing API is a controlled document-processing pipeline. Validate untrusted input, normalize it to PDF, select an authorized printer, negotiate supported attributes, render through one tested path, and track the job beyond the initial HTTP response.

The separation makes future changes manageable. You can replace the Word converter, introduce asynchronous workers, add secure-release printing, or integrate a cloud print provider without changing the public upload contract. Begin with PDF and one controlled printer, make that path observable, and add formats and options one at a time.

Build the narrow path first, measure it, and expand only when it is trustworthy.
