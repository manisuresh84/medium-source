n8n + Podman + MCP: Build a Local HR Automation with Webhooks and Model Context Protocol

Run a deterministic HR workflow locally, import it as JSON, and expose it through both HTTP and MCP tools.

By Suresh Kumar Mani

2026-08-08

Containers make applications repeatable. Workflow JSON makes automations repeatable. Webhooks give ordinary applications a simple HTTP boundary. Model Context Protocol (MCP) adds standardized discovery and invocation for tools. This tutorial combines all four—locally, deterministically, and without an LLM or cloud credential.

We will import a ready-made n8n workflow, call it directly with curl, then call the same webhook through a small MCP server. All employee details and policies are fictional.

Local HR automation with Webhooks and MCP tools.

What We Are Building

Both entry paths reuse the same deterministic workflow. Illustrative diagram.

The direct path is curl → n8n Webhook. The MCP path is MCP Client → Local MCP Server → n8n Webhook. MCP does not replace REST here; the webhook remains a normal HTTP integration boundary.

Why MCP?

A traditional API client must already know which endpoint to call and how its payload is shaped. An MCP client can ask a server which tools exist, inspect their descriptions and input schemas, and invoke a selected tool using the protocol.

An MCP host contains or manages an MCP client. That client connects to an MCP server over a transport. A server may expose tools, resources, and prompts. This tutorial focuses on tools: named capabilities with descriptions, typed inputs, handlers, and results.

For this local network service we use Streamable HTTP, the current HTTP transport. The official SDK documentation recommends stdio when a local client launches a server as a child process and Streamable HTTP for a network-accessible server. We bind it only to 127.0.0.1.

Prerequisites

Install Podman, Node.js 20 or later, npm, a browser, and either curl or PowerShell. Docker is a drop-in alternative for the basic container command.

Start n8n with Podman

mkdir -p ~/.n8n

podman run -it --rm \
  --name n8n \
  -p 5678:5678 \
  -v ~/.n8n:/home/node/.n8n \
  docker.n8n.io/n8nio/n8n

The startup command. Illustrative diagram; live image download was registry-rate-limited during capture.

-it attaches the terminal; --rm removes the stopped container; --name n8n supplies the name used by our import script; -p maps the UI port; and -v persists n8n data outside the disposable container. Open http://localhost:5678.

On Fedora, RHEL, or another SELinux-enforcing host, use :Z for this private bind mount: -v ~/.n8n:/home/node/.n8n:Z. Do not add it blindly on Windows, macOS, or non-SELinux systems. The Docker equivalent simply replaces podman with docker.

Import the Workflow Instead of Building It Manually

Instead of manually creating every node, import the supplied JSON workflow and start testing immediately.

Workflow JSON turns a multi-step UI setup into a repeatable deployment artifact. Illustrative diagram.

In the n8n editor, open the workflow menu, choose Import from File, select workflow/hr-leave-webhook.json, then save the imported workflow. Menu placement can change between releases.

Importing the supplied JSON. Illustrative diagram, not a fabricated n8n screenshot.

The CLI is faster and scriptable. Current n8n CLI documentation supports n8n import:workflow --input=<file>:

podman cp workflow/hr-leave-webhook.json n8n:/tmp/hr-leave-webhook.json
podman exec n8n n8n import:workflow --input=/tmp/hr-leave-webhook.json

The supplied podman/import-workflow.sh and PowerShell equivalent add existence and running-state checks. Refresh the browser afterward. Imports are inactive, and workflow exports do not contain credential secrets; this workflow needs no credentials.

As an alternative, mount the project workflow directory read-only with -v "$PWD/workflow:/imports:ro", then import /imports/hr-leave-webhook.json. On SELinux, the appropriate read-only label is commonly :ro,Z. podman cp is easier for beginners because it avoids host-path and labeling differences.

Explore the Imported n8n Workflow

The imported workflow uses built-in nodes only. Illustrative diagram.

The nodes are Webhook, Code, If, Edit Fields (Set), and Respond to Webhook. The Webhook accepts POST /hr-leave-request. Code normalizes and validates the body. If routes leaveDays <= 5 to AUTO_APPROVED; larger requests go to MANAGER_REVIEW.

This decision exists only to demonstrate branching. It is not a recommended HR policy.

n8n details that make the import reproducible

The Webhook is configured to respond through the Respond to Webhook node, rather than returning immediately from the trigger. Incoming JSON is normally available under $json.body, so the normalization code deliberately reads $json.body ?? $json to remain convenient in manual tests. Both branches reduce their output to the four public response fields before reaching the shared response node.

The imported workflow is inactive until you review and activate it. Its editor Test URL and active Production URL are different registrations, not aliases. Finally, the container is disposable but /home/node/.n8n is bind-mounted: stopping a --rm container removes the container while preserving the local n8n database and workflow configuration under ~/.n8n.

Test the Webhook Directly

Activate the workflow, then run:

./examples/webhook-curl.sh

The Production URL is http://localhost:5678/webhook/hr-leave-request and requires an active workflow. The Test URL contains /webhook-test/; open the Webhook node and select Listen for test event before sending its one-run test request.

The three-day response is:

{
  "success": true,
  "employeeId": "EMP-1042",
  "status": "AUTO_APPROVED",
  "message": "Leave request accepted by the tutorial policy."
}

Changing leaveDays to 10 returns MANAGER_REVIEW.

What Is an MCP Tool?

Tool name, description, schema, handler, and result. Illustrative diagram.

submit_leave_request declares a Zod input schema. The SDK turns it into a discoverable JSON schema and validates arguments before the handler runs. The handler performs an HTTP POST to N8N_WEBHOOK_URL, parses the JSON response, and returns both text content and structured content to the client.

That separation matters. The tool name is the stable capability identifier. Its description helps a person or compatible client understand when it applies. The schema defines what a valid call looks like. The handler contains the actual integration code. Finally, the tool result carries the outcome back over MCP. n8n remains responsible for workflow orchestration rather than MCP protocol details.

get_leave_policy returns the local fictional rule without contacting n8n. health_check reports whether the MCP process is healthy and whether n8n's /healthz endpoint is reachable. It never puts an internal stack trace in a normal tool result.

Start the MCP Server

npm install
N8N_WEBHOOK_URL=http://localhost:5678/webhook/hr-leave-request \
  npm --workspace mcp-server start

PowerShell:

$env:N8N_WEBHOOK_URL = 'http://localhost:5678/webhook/hr-leave-request'
npm --workspace mcp-server start

The Streamable HTTP endpoint is http://127.0.0.1:3001/mcp.

Discover and Call MCP Tools

Run the supplied official-SDK client:

npm --workspace mcp-client start

It connects, calls tools/list, prints all three names, and invokes submit_leave_request. To debug interactively, run npx @modelcontextprotocol/inspector, select Streamable HTTP, and enter the endpoint above.

The expected tools/list result. Illustrative diagram.

The request travels through MCP, into the tool handler, over ordinary HTTP to n8n, and back as an MCP tool result. No model chooses the tool; the client calls it deterministically.

How the Entire Request Flows

Tool discovery happens before invocation. Illustrative diagram.

n8n as an MCP Server vs n8n as an MCP Client

Native n8n can expose or consume MCP capabilities. Illustrative diagram.

Current n8n documentation lists three relevant nodes. MCP Server Trigger exposes connected workflow tools to MCP clients. The MCP Client core node can list or execute tools on an external MCP server. MCP Client Tool is an AI sub-node that supplies external MCP tools to an AI Agent, so that particular direction introduces an agent and usually a model credential.

n8n also documents an instance-level MCP server for authorized access to selected workflows. These native features are useful, but they are optional here. The standalone server makes tool registration and transport mechanics visible without requiring an agent.

Choose the native server direction when n8n should own the MCP endpoint and its connected workflow tools. Choose the client direction when an n8n workflow needs capabilities hosted elsewhere. Choose a small adapter like this tutorial's server when you want explicit protocol code, a carefully limited public tool surface, or to reuse an existing webhook without redesigning the workflow.

A native MCP workflow JSON is not supplied because the local n8n image could not be downloaded and runtime-validated during production. Publishing an unverified export would contradict the tutorial's reproducibility goal.

Security Note

Do not expose an unauthenticated MCP server or n8n webhook to the public internet. Production needs TLS, authentication, authorization, tool-level permissions, webhook protection, secret management, input limits, audit logs, container hardening, and workflow versioning.

MCP tool availability does not imply that a user is authorized to perform its action. Discovery, authentication, authorization, and business permission are separate concerns.

Never send medical information, government identifiers, Social Security numbers, salary or performance data, disciplinary records, protected characteristics, or real employee information through this sample. Real HR systems also require classification, retention, access, and audit policies.

The tutorial's loopback binding and Host-header check reduce accidental network exposure, but they are not authentication. A production server should also rate-limit requests, cap payload size, avoid returning implementation details, and authorize every tool call against the caller and affected employee scope.

What We Built

We ran n8n in Podman, imported workflow JSON, tested the webhook directly, registered three MCP tools with the official SDK, and sent the same request through MCP. The clean boundary is:

MCP Client → MCP Server → n8n Webhook → HR Workflow → MCP Result

Next steps might add authenticated manager approval, database persistence, OAuth, Teams or Slack notifications, Workday or ServiceNow integration, external MCP tools, or a separately secured n8n-native MCP workflow.
