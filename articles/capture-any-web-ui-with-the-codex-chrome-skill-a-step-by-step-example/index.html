Capture Any Web UI with the Codex Chrome Skill: A Step-by-Step Example

Use your existing Chrome session to navigate a web app, prepare its UI, and capture documentation-ready screenshots

By Suresh Kumar Mani

2026-08-14

The Codex Chrome skill can capture any UI that is visible and accessible in your Chrome session. Azure is one possible target, but it is not the point of the capability. The same workflow applies to GitHub, an internal admin console, a local development site, a monitoring dashboard, a support portal, or a SaaS application.

More importantly, the skill does more than take a static screenshot. It can navigate to the correct page, open a menu or panel, select filters, wait for the UI to update, and then capture the state that explains the workflow.

This tutorial proves that flow with a small example: documenting a local web application called Publishing Studio. We will capture an overview of the page and then a second viewport after scrolling to the preview and workflow controls.

What the Chrome skill can capture

Depending on the documentation goal, Codex can produce:

  • A viewport screenshot of exactly what is currently visible.
  • A full-page screenshot that includes content below the fold.
  • A focused capture of a panel, table, dialog, form, or workflow step.
  • A sequence of screenshots taken after different UI interactions.

The target does not need to be public. Because the skill can use your existing Chrome session, it can work with a site you have already signed into. You complete authentication yourself; Codex does not inspect stored credentials, read saved passwords, or bypass sign-in.

The sample task

Our goal is simple:

  1. Open the Publishing Studio web application.
  2. Capture the top of the page for orientation.
  3. Scroll to the editor preview and workflow controls.
  4. Capture that second state.
  5. Leave the application unchanged.

This example uses a local URL, but you can replace it with any site Chrome can open.

Step 1: Prepare Chrome

Enable the ChatGPT browser extension under Settings → Computer use. If the target application requires authentication, open it in Chrome and sign in yourself before starting the task.

For a private application, also check what may appear on screen. Names, email addresses, customer records, subscription identifiers, internal URLs, and access tokens should not be included unless they are necessary and safe to publish.

Step 2: Give Codex a scoped capture request

Use a prompt that defines the target, UI actions, required captures, and safety boundary:

Use my existing Chrome session. Open http://localhost:8088. Capture the initial viewport of Publishing Studio. Then scroll until the article preview and workflow controls are visible and capture a second viewport. Do not submit the article or change any form fields. Save both screenshots for a tutorial.

This is better than saying “take screenshots of my app.” It tells Codex what success looks like and prevents accidental state changes.

Step 3: Codex opens and verifies the page

Codex connects to Chrome, opens the requested URL, and reads the visible page state before acting. That verification matters. It confirms that the intended application loaded and provides reliable targets for later interactions.

The first screenshot establishes context: the product name, its purpose, the three-stage workflow, and the beginning of the authoring interface are visible together.

This is a viewport capture. It represents what a reader would see without scrolling and works well as the opening image in a tutorial.

Step 4: Codex prepares the next UI state

Next, Codex scrolls down within the same page. The goal is not simply to get a different picture; it is to reveal the controls involved in the next part of the workflow.

After the scroll, the preview, image-upload section, and Submit for approval control are visible. Codex then captures the updated viewport.

The two screenshots now form a useful sequence:

  • The first image answers, “Where am I and what does this application do?”
  • The second answers, “Where are the preview and publishing controls?”

No form was submitted and no application data was changed.

Step 5: Ask for focused captures when needed

For a more detailed guide, extend the request with specific UI states. For example:

Select Preview, scroll to Workflow controls, and capture only the right-side control panel. Then open the tags menu and capture the menu with its options visible. Do not select a tag or submit the form.

This pattern is useful for almost any web UI:

  • Open a GitHub Actions run and capture the failed job summary.
  • Apply a date filter in a monitoring dashboard and capture the chart with the filter visible.
  • Open a settings dialog and capture each tab without saving changes.
  • Filter a data table and capture the active filters together with the results.
  • Walk through a support workflow and capture every step before the final submission.

The best screenshots show both the result and enough UI context to explain how that result was produced.

Viewport, full-page, or focused panel?

Choose the smallest capture that communicates the lesson:

  • Use a viewport for page orientation or one screen-sized workflow step.
  • Use full-page when readers need the overall layout or content below the fold.
  • Use a focused panel for tables, dialogs, settings, errors, and other detail-heavy UI.
  • Use a sequence when the state changes after clicks, filters, or form input.

Full-page images are often too tall for Medium and difficult to read on a phone. A short sequence of focused images usually tells the story more clearly.

A reusable prompt template

Use this template for future capture tasks:

Use my existing Chrome session. Open [URL or application]. Navigate to [page or resource]. Perform these read-only UI actions: [tabs, filters, menus, scrolling]. Capture [viewport, full page, panel, dialog, or sequence] after [state to verify] is visible. Do not [submit, save, delete, restart, or change permissions]. Exclude [sensitive details] from the captures.

The template works equally well for public websites, local applications, and authenticated enterprise tools.

Safety and publishing checks

Before sharing a screenshot, review it for information that the tutorial does not need. Recapture or redact unnecessary customer data, account details, internal hostnames, IP addresses, resource identifiers, and personal information.

Also distinguish read-only interactions from mutations. Scrolling, opening tabs, and changing display filters are usually safe for documentation. Clicking Save, Delete, Publish, Restart, or Grant access changes external state and should be explicitly authorized.

The takeaway

The Codex Chrome skill is a general-purpose UI capture capability, not an Azure-specific tool. Its advantage is the combination of browser navigation, UI interaction, state verification, and screenshot capture inside the Chrome session you already use.

The Publishing Studio example demonstrates the complete loop: give Codex a scoped request, open and verify the application, capture the initial viewport, prepare a second UI state, and capture the controls that matter. Replace the sample URL and steps with your own application, and the same process becomes a repeatable way to build accurate visual documentation.
